# Toy Box

DIY toddler toy: a screen runs a set of mini-games, all driven from a phone/laptop on the LAN. Some games are controlled by a wireless motion **wand** — a CodeCell C6 (ESP32-C6 + BNO085 9-axis IMU) that streams orientation and motion over WiFi UDP to a Go `wand` package games consume; others (like flashcards) just use the screen. The product brand shown on screen is "TOY BOX" (or "EMMA'S TOY BOX"); "wand" refers only to the physical controller.

## Architecture

```
CodeCell C6 ──UDP 40Hz──> Go "wand" package ──> App (web-controlled splash + games)
                                                      ▲
                          phone/laptop ──LAN HTTP──> pkg/control (always-on, :8080)
```

- **Firmware** (`firmware/wand_controller/`): Arduino sketch. Reads IMU via CodeCell library, applies a configurable wand-frame remap quaternion (`WAND_REMAP_*` in `config.h`), sends 44-byte UDP packets at 40Hz. Uses a discovery handshake (broadcast → ack) then unicasts to the discovered listener. Auto-recovers to discovery mode on client disconnect (ack timeout + send failure tracking + UDP socket reinit). **WiFi is provisioned on-device** via a WiFiManager captive portal (`connectWiFi()`): no credentials are compiled in. WiFiManager owns the saved creds (a portal-provisioned network wins on every boot); `config.h`'s `WIFI_SSID`/`WIFI_PASSWORD` only **seed a never-provisioned wand** (dev/CI) — `preloadWiFi` is gated on `!getWiFiIsSaved()` so it can't override a real saved network. When no saved creds connect, the wand opens an open AP **"Toy Box Wand Setup"** (onboard LED solid blue) for a phone to configure. Portal times out (180s) → reboot-retry; a prolonged runtime disconnect (>2 min, e.g. router/password change) also reboots so setup re-opens.
- **Vendored libraries** (`firmware/libraries/`): The Makefile's `arduino-cli` invocation uses `--libraries firmware/libraries` so these copies win over any globally installed one. Two are vendored: (1) [CodeCell](https://github.com/microbotsio/CodeCell) with a small patch adding `Motion_RotationNoMagVectorRead(w, x, y, z)` so we can read the no-mag game rotation quaternion directly (upstream only exposes it as Euler angles — see `PATCHES.md` there); (2) [WiFiManager](https://github.com/tzapu/WiFiManager) v2.0.17, unmodified, for the WiFi setup portal.
- **Wand package** (`wand/`, import `github.com/anthonyrego/toybox/wand`): `wand.New(port)` / `Start()` / `State()` / `Stop()`. The motion-controller listener — a subpackage of the toybox module, not the umbrella. Background goroutine reads UDP, stores latest state in `atomic.Value` for lock-free reads from the game loop. Defines a minimal zero-dependency `wand.Quat` type; games convert to `mgl32.Quat` at the call site.
- **App** (`cmd/play/`): Single entry point. Creates the shared wand listener, the name/video/nav stores and the always-on control server (`pkg/control`, port 8080), snapshots the display's selectable resolutions, registers games (each a `GameDef` with a stable `ID` slug), and runs the `App` wrapper. The screen is a pure display — there is no keyboard control except **Esc pressed three times** to quit (a small top-left on-screen counter shows the countdown).
- **Games** (`games/`): `App` wrapper (`app.go`) implements `engine.Game` and delegates to a boot/idle **splash** or the active game. Each frame it polls the control server's nav store for a requested game switch (performing it on the loop thread and swapping the active game's web module) and the video store for apply-on-save display changes. `GameDef` registry (`games.go`) carries `{ID, Name, New}`. Games implement `engine.Game`, receive the shared wand listener, and may optionally implement `WebProvider` (`WebModule() control.GameModule`) to contribute a per-game web page editable while they run. Games consume `State.Q` (quaternion) directly; **never** subtract two Euler triples to compute a rotation delta — use `q_rel = q_neutral.Conjugate().Mul(q_current)` (or the mgl32 equivalent) for a true body-frame delta. Wand games don't auto-capture neutral on the first frame: they embed a shared `*calibration.Calibrator` (`games/calibration`, import `github.com/anthonyrego/toybox/games/calibration`) whose `Track(q)` folds in a web-requested calibration and returns the body-frame delta (identity until the first calibrate, so the game holds at neutral). Each exposes a **Calibrate** button on its web page (a `control.SettingButton` Setting — via `Calibrator` directly for slider-less games, or `calibration.WithCalibrate(model, c)` to append it to an existing `SettingsModel`) and implements the `games.CalibrationPrompter` interface (`NeedsCalibration() bool`), so `App.Overlay` draws a centered "hold your wand pointing straight up, then press Calibrate" prompt (dim panel + up-arrow + text) until the player calibrates.
  - **Color Sphere** (`games/colorsphere/`): Inward-facing color sphere whose orientation follows the wand. Captures a neutral quaternion when the player presses **Calibrate** on the web page (shared `games/calibration` helper); the sphere's rotation is the body-frame delta from neutral, so whatever pose the wand is held in at calibration becomes "zero." Plus a linear-accel-driven particle river. First game, for babies 10 months+.
  - **Flying** (`games/flying/`): Flight simulator. Captures a neutral quaternion when the player presses **Calibrate** on the web page; each frame computes the body-frame delta and uses the imaginary parts (`2 * qRel.{X,Y,Z}`) as pitch/roll/yaw rate inputs. No gimbal lock, no axis entanglement.
  - **Drum Circle** (`games/drumcircle/`): Uses linear accel magnitude for hit detection (gravity-free — no threshold hack) and rotates a **calibrated** body-frame tip vector (`qRel.Rotate({1,0,0})`, qRel from the shared `games/calibration` helper) against an icosahedron face map for note selection. Synthesizes tones through `pkg/audio`. Its hit/trail tunables live in a mutex-guarded `tuning` (`tuning.go`) exposed as a `control.SettingsModel`, so they render as live sliders on the game's web page; `Update` reads a per-frame `snapshot()`.
  - **Flashcards** (`games/flashcard/`): Web-managed picture/name display; the wand is unused. Contributes a `control.GameModule` to the unified control server while active (no listener of its own): its embedded vanilla-JS SPA served at `/game`, its REST under `/api/game/*` (add/remove/rename/reorder/select-current; the SPA prefixes `BASE="/api/game"` onto its existing `/api/...` paths, and the server strips that prefix so the inner mux is unchanged). The deck persists to disk (`~/.toybox/flashcards`, JSON manifest + PNGs) and reloads on startup. Each card has a **name and one or more photos** (`Card.Photos []Photo{ID,File}`, each photo a distinct PNG + GPU texture keyed by photo ID); the on-screen selection is a card (`currentID`) plus a photo index within it (`currentPhoto`), and a parent cycles photos from the web UI (`POST /api/photo/{next,prev}`) or jumps straight to one (`POST /api/current` with an optional `photo` index). Per-card photo management: `POST /api/cards/{id}/photos`, `DELETE /api/cards/{id}/photos/{photoId}` (no-op on a card's last photo — delete the card instead), `GET /api/cards/{id}/photos/{photoId}/image`. Legacy single-image manifests (`Card.File`) migrate to the photos model on load. Renders the current photo as a flat quad through the **lit pipeline's UV texture path** (`Renderer.BindLitTexture` binds the image into fragment sampler slot 1; lighting is pure-white ambient with no sun/point lights so the quad shows exact texture colors — no new shaders needed). The card name (plus a small "2 / 5" counter when multiple photos) is drawn as full-resolution 2D overlay text. Concurrency: the HTTP goroutine only mutates a mutex-guarded `store` (CPU bytes, never GPU); the game loop diffs a revision counter each frame and does all `CreateTextureFromRGBA`/`ReleaseTexture` work on the loop thread. Env override: `TOYBOX_FLASHCARD_DIR` (default `~/.toybox/flashcards`).
  - **Splash** (`games/splash/`): Boot/idle screen shown at launch and whenever no game is running (game choice is web-only — no auto-launch; quitting a game returns here). Shows the connect URL plus a QR code of it (encoded by `control.QRCodeRGBA`, uploaded as a texture and drawn through the lit pipeline's UV path like the flashcard images), and the personalized title from a `TitleProvider` ("EMMA'S TOY BOX" / "TOY BOX"), rebuilt live (revision counter) when the name changes from the web.
- **Web control** (`pkg/control`): The single always-on `net/http` server (port 8080, `TOYBOX_CONTROL_PORT`), started for the app's whole life in `cmd/play/main.go` — the only control surface. App-level REST: `GET`/`POST /api/profile` (owner name), `GET /api/games` + `GET`/`POST /api/current` (list/report/switch the active game; the response's `hasPage` tells the web shell whether to load the per-game iframe), `GET`/`POST /api/video` + `GET /api/video/modes` (display settings + the display's selectable resolutions). The active game's optional web module is mounted under `/game` (its page) and `/api/game/*` (its REST), both forwarded to a mutex-guarded `active GameModule` pointer the App swaps on every switch; an `RWMutex` held across each dispatch is the barrier that lets `SetActiveModule(nil)` wait out in-flight handlers before the outgoing game is destroyed. **Loop-thread-safe invariant**: handlers touch only mutex-guarded CPU stores (name/video/nav and the game's own state) — never SDL/GPU; all GPU work stays on the game loop via revision diffs. Stores: `profile.Store` (sub-package `pkg/control/profile` — owner name + `Title`/`WindowTitle`/`CleanName`/`Dir`, persisted to `~/.toybox/profile.json`; `Title` → "EMMA'S TOY BOX"/"TOY BOX", `WindowTitle` → the proper-case OS window title; names cleaned to printable ASCII and capped at 24 chars), `VideoStore` (display settings persisted to `~/.toybox/settings.json`, applied on save by the App), `NavStore` (the game-switch channel; the game list crosses as `[]GameInfo` data so `pkg/control` never imports `games`). Simple games get a page for free: a `[]Setting` descriptor (`SettingsModel`) wrapped by `NewSettingsModule` into a `GameModule`, rendered by the embedded generic-settings SPA (each `Setting` is a slider, `SettingFloat`, or an action button, `SettingButton`, whose press arrives as `Apply(key, 1)`). Embedded app-shell SPA (Games / Now Playing / Settings tabs) + generic SPA. Env: `TOYBOX_CONTROL_PORT` (default 8080), `TOYBOX_CONFIG_DIR` (default `~/.toybox`). No auth — home-LAN toddler toy, binds all interfaces.
- **Engine** (`pkg/`): Lightweight 3D engine built on SDL3 GPU API. Packages: `engine` (game loop; `ApplyDisplaySettings` is the apply-on-save entry, called from `App.Update` on the loop thread), `renderer` (GPU pipelines, shaders, draw calls, post-processing; the HDR swapchain path remains but is dormant/off), `window` (SDL3 window + GPU device; `DisplayModes()` enumerates resolutions), `camera` (view/projection, frustum culling), `input` (keyboard/mouse), `mesh` (primitives + texture loading), `audio` (SDL3 audio output device wrapper for procedural synthesis), `ui` (8x8 pixel-font text meshes — `NewTextMesh`/`TextWidth`/`FontScale`; the pause menu was removed when control moved to the web), `settings` (JSON display settings, now persisted via `pkg/control`), `control` (the always-on web control server + its `profile` sub-package), `sign` (pixel font), `shaders` (embedded compiled shaders for Metal/Vulkan/D3D12).
- **Protocol** (`protocol.go`): 44-byte data packets, little-endian. Magic `0x57 0x44`, version `0x02`, seq byte, then 10 float32s: quaternion w/x/y/z (unit, wand body frame), linear accel x/y/z (m/s², gravity-compensated), gyro x/y/z (°/s). Also 4-byte control packets for discovery (`0x01`) and ack (`0x02`). `State.Euler()` provides a ZYX decomposition for cosmetic uses only.
- **Distribution** (`.goreleaser.yaml` + `.github/workflows/release.yml`): Pushing a `v*` tag triggers GitHub Actions → GoReleaser cross-compiles `cmd/play` (binary `toybox`) for macOS (one **universal** Intel+Apple-Silicon binary), Windows, and Linux × amd64/arm64, and publishes a Release with archives (`toybox` + `README` + `LICENSE`) and `checksums.txt`. No cgo (go-sdl3 is purego) and SDL3 is embedded via `binsdl`, so the binaries need no SDL toolchain; macOS/Windows/Linux-amd64 are self-contained, while Linux-arm64 (Raspberry Pi) needs system `libSDL3` at runtime. **The job runs on a macOS runner** — a Linux-cross-built darwin binary is a malformed Mach-O that crashes under Rosetta — and there GoReleaser signs (Developer ID) + notarizes the universal macOS binary via the Apple Notary API, gated on `MACOS_*` secrets (see `docs/RELEASING.md`). A post-GoReleaser workflow step (`scripts/package-macos.sh`) then wraps that universal binary in a double-clickable, signed + notarized + **stapled** `Toy Box.app` inside a `.dmg` and attaches it to the release (a bare unix binary can't be Finder-double-clicked; the `.tar.gz` keeps it for terminal use). `version` (`cmd/play/main.go`, printed at startup) is stamped via `-ldflags -X main.version`; `make release-snapshot` dry-runs the whole build into `dist/` (gitignored) without publishing or signing.

## Hardware

- **CodeCell C6**: ESP32-C6, BNO085 IMU, WiFi 6 + BLE 5, USB-C LiPo charging, Arduino-compatible
- CodeCell library API (used): `Init(MOTION_ROTATION_NO_MAG + MOTION_LINEAR_ACC + MOTION_GYRO)`, `Run(40)` (Hz), `Motion_RotationNoMagVectorRead(w,x,y,z)` (**locally patched** — see `firmware/libraries/CodeCell/PATCHES.md`), `Motion_LinearAccRead()`, `Motion_GyroRead()`

## Commands

```
make play                  # run the app (web-controlled games)
make monitor               # display live IMU readings in terminal
make compile               # compile firmware
make upload                # compile + flash firmware to device
make test                  # run all Go tests
make sim                   # send fake IMU data (no hardware needed)
make release-snapshot      # dry-run a cross-platform release build into dist/
```

## Integration

The `wand` package (UDP listener, `wand/`) has zero external dependencies. The `pkg/` engine packages depend on SDL3 and mathgl (plus `skip2/go-qrcode` in `pkg/control` for the splash QR). To add a new game: create a package under `games/`, implement `engine.Game`, and add a `GameDef` (`{ID, Name, New}`, with a stable `ID` slug) in `cmd/play/main.go`. The shared wand listener is passed to each game's constructor. To give the game a web page, implement `WebProvider` returning a `control.GameModule` — a custom one (like flashcards) or `control.NewSettingsModule` over a `SettingsModel` (like drum circle). `pkg/control` must not import `games` (the game list crosses as `[]control.GameInfo` data).
